# Changelog

All notable changes to this package are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

First standalone release. ActiveRecord moves out of the PRADO framework (`framework/Data/ActiveRecord` and the `prado-cli` action `framework/Shell/Actions/TActiveRecordAction.php`) into this package. Namespaces and class names are unchanged. The baseline is the framework copy in PRADO `master` at commit `165efc3a8` (2026-10-23). The entries below are differences from that baseline. See the [migration guide](docs/migration.md) for upgrade steps.

### Added

- `composer.json` declares `extra.prado` for PRADO 4.4: `bootstrap` (`TActiveRecordConfig`), `error-messages` (`src/Data/ActiveRecord/Exceptions/messages.txt`), and `class-map` (`config/classes.json`). The legacy top-level `extra.bootstrap` remains for PRADO 4.3.
- `config/classes.json` maps the 31 short class names (`TActiveRecord`, `TActiveRecordConfig`, `TScaffoldListView`, `TActiveRecordAction`, ...) to their FQNs. It replaces the ActiveRecord entries of the framework's `classes.php`.
- Message text for four codes that were thrown without a definition: `ar_save_invalid` (`save()` on a deleted record), `ar_delete_invalid` (`delete()` on a new or already deleted record), `ar_data_invalid` (`copyFrom()` with a value that is neither array nor object), and `ar_belongs_to_multiple_result` (a `BELONGS_TO` or `HAS_ONE` relation that matched several rows). These exceptions previously carried the bare code as their message. The same file now defines the five `scaffold_*` codes the Scaffold controls raise as `TConfigurationException` (`scaffold_invalid_record_pk`, `scaffold_invalid_record_class`, `scaffold_unable_to_find_edit_view`, `scaffold_unable_to_find_list_view`, `scaffold_invalid_edit_renderer`), which the framework never defined either.
- `tests/unit/Shell/Actions/TActiveRecordActionTest.php` and `tests/unit/Data/ActiveRecord/Exceptions/TActiveRecordExceptionTest.php`: the first covers the `generate` flag parsing below, the second fails when a code is thrown without message text.
- `TActiveRecord::getViewData()` and `setViewData()`: the record side of PRADO 4.4's `Prado\Web\UI\IViewDataModel` contract, provided by name so a record also runs on PRADO 4.3. `getViewData()` returns the column properties in declaration order, then one entry per `$RELATIONS` key (`HAS_MANY` and `MANY_TO_MANY` as a list, `BELONGS_TO` and `HAS_ONE` as the related record). `setViewData()` assigns column properties and ignores relation and unknown keys. `TTemplateControl::tryToUpdateView()` and `tryToUpdateModel()` call them in place of the framework's former direct use of `TActiveRecord::BELONGS_TO`, `HAS_ONE`, and `HAS_MANY`. `tests/unit/Data/ActiveRecord/TActiveRecordViewDataTest.php` covers both.
- `TActiveRecordConfig::installShellAction()` registers `TActiveRecordAction` with a `TShellApplication` during `init()`. In the framework, `TShellApplication::installShellActions()` registered the action when a `TActiveRecordConfig` module was present. The module now registers the action itself, so the framework no longer references the class. `prado-cli activerecord/generate` and `generate-all` are available under the same condition as before.

- `composer coverage` and `composer coverage-html` measure line coverage of `src/` over the `unit` and `db-sqlite` suites with Xdebug. `phpunit.xml` declares `src/` as the coverage source. The two suites cover every line of the core classes and of `TActiveRecordAction`.
- `TActiveRecord::__isset()` and `__unset()` for relations that the class does not declare as properties. `isset($record->relation)` is true when the relation is loaded or assigned and not null; it does not load the relation. `unset($record->relation)` discards the value, so the next read loads it again.

### Changed

- Tests are grouped by what they need. `tests/unit/Data/ActiveRecord/DbSpecific/Mysql` (the `db-mysql` suite) holds the tests that read and write the `prado_unitest` MySQL database; `DbSpecific/Sqlite` (the `db-sqlite` suite) holds the tests that use the bundled SQLite files in `tests/unit/Data/ActiveRecord/sqlite`; everything else is the `unit` suite and needs no database. `TScaffoldInputBaseTest` moves from the framework's `tests/unit/Data/DbCommon` to `tests/unit/Data/ActiveRecord/Scaffold/InputBuilder`.
- The database tests run on every PDO driver PRADO supports. The tests are abstract cases under `tests/unit/Data/ActiveRecord/DbSpecific/Cases/`; each driver directory (`Mysql`, `Sqlite`, `Pgsql`, `Sqlsrv`, `Firebird`, `Oracle`, `Ibm`) subclasses every case with a connection trait over `PradoUnitActiveRecordConnectionTrait`, and `tests/unit/Data/ActiveRecord/scripts/<driver>/database.sql` holds the same schema per dialect, cut from the framework's `tests/initdb_mysql.sql`. The fixture column `order` is `sort_key` and the table `Users` is `users`, so the schema needs no quoting on any driver, and the records map upper case column names for Firebird, Oracle, and DB2. CI runs one job per database, with the setup scripts under `.github/scripts/`. A case skips with the reason on a driver that lacks a feature: composite primary keys on SQLite, whose framework metadata reports only the first key column; the composite-key `IN` form on SQL Server, Firebird, and DB2; identity read-back on Oracle and Firebird; NULL parameters on DB2.

### Fixed

- `prado-cli activerecord/generate` and `activerecord/generate-all` honor the `soap` and `overwrite` arguments. `actionGenerate()` stored the flags in fields the generator never read, so `@soapproperty` docblocks were never written and an existing file was always skipped. `generate-all` also joined the flags into a command line string in which a `false` first flag shifted `overwrite` into the `soap` position. The flags are now passed positionally, and `generate()` passes its tokens through unchanged.
- `MANY_TO_MANY` relations that name the association table's foreign key columns, as in `'player_skills.(player_id, skill_id)'`, split the column list on commas and spaces. The pattern matched a literal `*` instead of whitespace, so the list stayed one column name.
- Self-referencing `MANY_TO_MANY` relations, whose association table holds two foreign keys to the same table, join the source key to one column and the foreign key to the other ([#4](https://github.com/pradosoft/prado-activerecord/issues/4)). Both lookups took the first matching key, so a record was returned as its own related record, or the relation was empty, depending on the order the keys were declared. `TActiveRecordRelation::findForeignKeys()` takes an optional list of columns to exclude. `TActiveRecordHasManyAssociation` excludes the named association columns (`'links.target_id'`) from the source key, and the source key columns from the foreign key. Writing the association rows uses the same keys. The SQLite metadata reports all keys to one table as a single entry, so `findForeignKeys()` splits an entry where a referenced column repeats. `tests/unit/Data/ActiveRecord/DbSpecific/Sqlite/SelfManyToManyTest.php` covers both declaration orders.
- A relation that the record class does not declare as a property loads once. Since PRADO's change to `$_relationsObjs` (framework commit `6ddd140bf`), every read queried the database again, so `withX()` eager loading and assigned values were discarded on the next read. A `HAS_ONE` relation with no match raised an undefined array key warning. Relation names are case-insensitive, and the value is kept under the declared key, so `$record->Players` and `$record->players` read the same value.
- `HAS_ONE` relations set the property to null when no record matches, as `BELONGS_TO` relations do.
- Relation lookups skip records whose key is null. The framework quoted the null (a PHP 8.1 deprecation) and, for `MANY_TO_MANY`, ran a query that matched nothing.
- Finders leave the caller's `TActiveRecordCriteria` unchanged. `find()` and `findBySql()` set its limit to 1, so a later `findAll()` with the same object returned one record. A criteria passed to `withX($criteria)`, or a relation handler used twice, accumulated the key condition of each query.
- Records keep the connection of the finder that read them, so `save()` and `delete()` go to the same database. A finder bound to a connection with `setDbConnection()` returned records that wrote through the manager's default connection. `MANY_TO_MANY` records use the foreign finder's connection.
- Records on connections with the same connection string use their own connection. The gateway shared one command per connection string, and its builder kept the first connection, so a second `sqlite::memory:` database, or a second login to the same server, read and wrote the first. Table information is kept per connection object; the application cache key is unchanged.
- `TActiveRecordRelationContext::updateAssociatedRecords()` saves `HAS_MANY` and `MANY_TO_MANY` records held in a relation the class does not declare. Reading the relation by reference raised an "Indirect modification of overloaded property" notice.
- `RecordClass::finder()` returns a finder for the class when the class does not override `finder()`. The default class name was `TActiveRecord`, which cannot be instantiated.
- A record class without `TABLE` or `table()` maps to its class name without the namespace, in lower case. The namespace was part of the table name.
- Dynamic finders named only by their prefix, such as `findBy()` or `with()`, no longer raise an uninitialized string offset warning.
- `prado-cli activerecord/generate-all` reports a missing connection or an unsupported driver as an error. Both stopped with a PHP fatal error. It closes the connection after generating, and only when it opened it, so an in-memory SQLite database keeps its tables.
- `prado-cli activerecord/generate` reports a missing table as an error. The table lookup threw a `TDbException` before the message could show. A missing connection without a `TActiveRecordConfig` module no longer stops with a PHP fatal error.
- `prado-cli activerecord/generate` writes only below the application base path. The path check compared string prefixes, so `<app>/../Outside.php` and a sibling directory such as `<app>2` passed, and a base path given through a symbolic link or with `..` rejected every output. Paths are resolved with `realpath()` and compared by directory. The error message names the namespace when the alias is unknown.
- `prado-cli activerecord/generate-all` replaces characters that are not valid in a PHP class name, such as `-` in `line-items`, with `_`. `TABLE` keeps the table name.
- The generated class docblock writes the time on a 24-hour clock. The format had no AM/PM marker.
- `TScaffoldListView` sorts by the selected option. The sort column and direction were passed as a list, so every sort failed with an invalid column name `0`. A row with a NULL column no longer raises an `htmlspecialchars()` deprecation.
- `TScaffoldBase` raises `scaffold_invalid_record_pk` with the key values when the edit view's record is not found. The array key raised an "Array to string conversion" warning instead.
- A subclass of a Scaffold control in another directory publishes the package's `style.css` unless its own directory has one. It failed to publish a stylesheet that did not exist.
- `TScaffoldSearch` trims `SearchableFields`, so a leading or trailing space no longer names an invalid column.
- The Scaffold input builder supports the `sqlsrv` and `dblib` drivers with `TMssqlScaffoldInput`, as the framework metadata does. A custom-driver handler that returns a value other than a class name raises `ar_not_input_base` instead of a `TypeError`.
- Scaffold time and date-time inputs save two-digit minutes and seconds (`13:05:09`). The year list includes the stored year when it lies outside the current year ±10, so saving keeps it.
- Scaffold set and enum inputs accept a NULL value, and an enum with no selection saves NULL instead of failing. The validator messages read "Please enter".
- `TMysqlScaffoldInput` returns the integer control for integer columns wider than one digit. `TMssqlScaffoldInput` reads `bit` checkboxes as booleans.
- `TSqliteScaffoldInput` selects minutes and seconds below 10 and treats only numeric `timestamp` values as Unix times. Text timestamps, such as a `CURRENT_TIMESTAMP` default, display and save as text.
